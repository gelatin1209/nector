Directory structure

Paths are relative to the extracted package root. Move the complete directory as one unit so relative resource and runtime paths continue to work.

On Windows, shared libraries are in library and import libraries are in library/static. Import libraries use exact DLL base names such as Nector.dll.a and NImation.dll.a, without a lib prefix; pass their full paths to the linker. Linux and macOS use their normal shared-library extensions and naming conventions. Only binaries matching the host platform and architecture can be loaded.

library/build-info.txt is at the library root, alongside the shared libraries. It is not in library/static or metadata.

Environment and metadata

The environment scripts derive paths from the package location rather than requiring a fixed installation directory. They set include, link, tool, asset, locale, configuration, and font variables, plus Nector_DIR and PKG_CONFIG_PATH for build-system integration. Windows adds library to PATH so tools can find their DLLs beside the executables; the shell script configures the appropriate runtime library path on Linux or macOS.

metadata/nector.json records the common directory map, default locale, and default font. Platform JSON files describe platform-specific library and environment settings. metadata/version.txt records the package, ABI, and package-layout versions.

CMake package

Consume the release with find_package(Nector CONFIG REQUIRED). If necessary, set Nector_DIR to the directory containing NectorConfig.cmake.

find_package(Nector CONFIG REQUIRED)
add_executable(my_app main.cpp)
target_compile_features(my_app PRIVATE cxx_std_17)
target_link_libraries(my_app PRIVATE Nector::nector Nector::nector_dsl_compile)
TargetPurpose
Nector::nectorMonolithic Nector implementation.
Nector::nector_dsl_compileDSL compilation and data-package loading.
Nector::nector_<module>Individual module, where <module> is core, rasterization, font, image, nimation, input, scene, audio, platform, or interface.

Use the monolithic target for the simplest integration, or link the modular targets required by the application. Keep runtime shared-library discovery configured when launching the built program.

pkg-config

The release supplies library/pkgconfig/nector.pc. The environment scripts add its containing directory to PKG_CONFIG_PATH; after loading the environment on Linux or macOS, query the compiler and linker flags:

pkg-config --modversion nector
pkg-config --cflags --libs nector
c++ -std=c++17 main.cpp $(pkg-config --cflags --libs nector) -o my_app

The version query and flag output can also be used by build-system discovery. The package name passed to pkg-config is nector, without the .pc suffix.

Manifest, checksums, and build information

  • metadata/manifest.json inventories relative file paths, sizes, and SHA-256 hashes. It excludes itself and the checksum file.
  • metadata/checksums.sha256 covers every package file except itself, including the manifest. From the package root, systems with sha256sum can run sha256sum -c metadata/checksums.sha256.
  • library/build-info.txt identifies build-specific information for the binary release and should remain with the library files. Normal development builds preserve it; only an explicit release build regenerates it.

Keep license with redistributed packages. The individual notices contain the authoritative Nector and third-party license terms.
